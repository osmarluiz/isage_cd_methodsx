\subsection{Overview}
\label{sec:overview}

The software shows two images of the same place at different dates
side by side (Figure~\ref{fig:overview}). The pipeline alternates
two steps, annotation and training. At each iteration the user sees
where the model improved and where it did not, and adds points
where they expect the most benefit, usually error regions. The loop
runs inside a session, a directory structure that versions the
dataset, the models, and the iterations automatically.

\subsection{Session structure}
\label{sec:session_structure}

A session is a single directory that contains the images, the class
configuration, the per-iteration annotations, and the training
artefacts:

\begin{tcolorbox}[enhanced, colback=treebg, frame hidden, boxrule=0pt,
    borderline west={2pt}{0pt}{treefolder}, arc=1.5pt,
    left=10pt, right=8pt, top=8pt, bottom=8pt]
\renewcommand*\DTstyle{\ttfamily\footnotesize}
\newcommand*\treedir[1]{\textcolor{treefolder}{\bfseries #1}}
\renewcommand*\DTcomment[1]{\hfill{\color{treecomment}\rmfamily\footnotesize\itshape #1}}
\dirtree{%
.1 \treedir{Sessions/CD/}.
.2 \treedir{config/}.
.3 session\_config.json\DTcomment{current\_iteration, format}.
.3 dataset\_metadata.json\DTcomment{classes, colors, ignore\_index}.
.2 \treedir{data/dataset/train/}.
.3 \treedir{<scene>/}\DTcomment{one folder per scene}.
.4 202106.png\DTcomment{dated, co-registered images}.
.4 202108.png\DTcomment{name = YYYYMM or YYYYMMDD}.
.4 202206.png.
.2 \treedir{iteration\_0/}.
.3 \treedir{annotations/}\DTcomment{one folder per scene, JSON per pair}.
.3 \treedir{predictions/}\DTcomment{per-pair prediction PNGs}.
.3 \treedir{models/}\DTcomment{trained checkpoints}.
.3 \treedir{masks/}\DTcomment{optional dense masks}.
.2 \treedir{iteration\_1/} \ldots.
}
\end{tcolorbox}

Each scene folder is a pool of dates. The file name is the date, as
a digit string whose lexicographic order is the chronological
order, so the tool compares strings and never parses calendars.
Which two dates form a pair is not fixed at build time. Any
(before, after) choice made in the interface is a valid pair, and a
scene with $n$ dates offers $n(n-1)/2$ of them.

Two configuration files sit under \texttt{config/}.
\pth{session_config.json} names the iteration the user is
currently annotating. \pth{dataset_metadata.json} declares the
classes: how many there are, which index means ``unlabeled'', and,
for each class, a name and a display colour. The interface, the
label files, and the prediction overlays all read class semantics
from this one file.

A helper script builds the session from a folder with one
subdirectory per scene, each holding two or more dated,
co-registered images, plus a classes file (a JSON list of
name and color in index order):

\begin{verbatim}
python tools/build_session.py entrada/ \
    --classes classes.json --out Sessions/CD
\end{verbatim}

The script copies the dated images into \texttt{train/<scene>/},
writes the two configuration files, and creates an empty
\texttt{iteration\_0/} with the four subfolders above. The session
is ready to open. The tool reads PNG and works in pixel
coordinates, with no notion of a coordinate reference system, so
co-registration, resampling and any georeferencing of the results
are upstream and downstream concerns. All images of a scene are
assumed to share one pixel grid.

\subsection{Pair-anchored label format}
\label{sec:label_format}

Every click lands in a JSON file that belongs to one pair. The path
is fully determined by the pair: a click on scene \texttt{0000}
with dates (\texttt{202106}, \texttt{202206}) at iteration
\texttt{5} goes to
\pth{iteration_5/annotations/0000/202106_202206.json}:

\begin{tcolorbox}[enhanced, colback=treebg, frame hidden, boxrule=0pt,
    borderline west={2pt}{0pt}{jsonkey}, arc=1.5pt,
    left=10pt, right=8pt, top=8pt, bottom=8pt]
\begin{Verbatim}[commandchars=\\\{\},fontsize=\footnotesize]
\jp{\{}
  \jk{"format_version"}\jp{:} \js{"3.0-pool"}\jp{,}
  \jk{"image"}\jp{:} \jp{\{}\jk{"name"}\jp{:} \js{"0000/202206.png"}\jp{,}
            \jk{"width"}\jp{:} \jn{1024}\jp{,} \jk{"height"}\jp{:} \jn{1024}\jp{\}}\jp{,}
  \jk{"iteration"}\jp{:} \jn{5}\jp{,}
  \jk{"created_at"}\jp{:} \js{"2026-08-07T15:30:00Z"}\jp{,}
  \jk{"pair"}\jp{:} \jp{\{}
    \jk{"scene"}\jp{:} \js{"0000"}\jp{,}
    \jk{"date_before"}\jp{:} \js{"202106"}\jp{,}
    \jk{"date_after"}\jp{:} \js{"202206"}
  \jp{\}}\jp{,}
  \jk{"annotations"}\jp{:} \jp{[}
    \jp{[}\jn{268}\jp{,} \jn{339}\jp{,} \jn{1}\jp{]}\jp{,}
    \jp{[}\jn{512}\jp{,} \jn{480}\jp{,} \jn{0}\jp{]}\jp{,}
    \jp{[}\jn{745}\jp{,} \jn{621}\jp{,} \jn{1}\jp{]}
  \jp{]}
\jp{\}}
\end{Verbatim}
\end{tcolorbox}

A point is an entry of \texttt{annotations}: pixel coordinates and
a class index. Anchoring the file to the pair preserves the
semantics of a change label. The same region can be change against
one before date and no change against another, and each statement
lives in its own file, so neither contaminates the other.

The file is rewritten at every click, so there is no save button
and no unsaved state. Every write is atomic. The annotator
serialises the JSON to a temporary file and only then renames it
into place, so a crash mid-write cannot leave a half-written file
on disk. A pair whose
point set becomes empty has its file removed, and the scene folder
is removed with its last pair. The file tree is always a faithful
representation of the current annotation.

Each JSON is one training sample, so downstream pipelines consume
the annotation tree directly, and a leakage-free train/validation
split reduces to selecting scene folders. All pairs of a scene live
in the same folder, so no split can place two pairs of the same
scene on different sides of the partition.

% 4.4 Bi-temporal annotation interface
% -------------------------------------------------------------
\subsection{Bi-temporal annotation interface}
\label{sec:ui}

Opening a session presents two synchronized canvases
(Figure~\ref{fig:overview}), before on the left, after on the
right. Zoom, pan, and points are mirrored between them, and a click
on either side lands the point at the same pixel on both.

Labeling takes few gestures: a left click adds a point with the
selected class, a right click near a point removes it, a drag
fine-tunes its position, the wheel zooms, a middle-mouse drag pans.
Point colours follow the class palette declared in
\pth{dataset_metadata.json}.

Each canvas has a date selector. The before selector offers only
dates earlier than the current after date, so an invalid pair
cannot be selected, and changing either date switches the point set
on both canvases. Dates already annotated are marked with a bullet,
a scene opens on its most recently annotated pair, and live
counters track the session, the scene, and the pair on screen.

The two selectors move within a scene. Moving between scenes is
the arrow keys, or the previous and next buttons below the
canvases, and a scene can also be reached by its index. Leaving a
scene needs no confirmation, since every click is already on disk.

\subsection{Training in the loop}
\label{sec:training}

iSAGE-CD deliberately ships without a trainer, because the loop
needs a model in it rather than a model inside the tool, and users
of an annotation tool want to bring their own architecture.
Training plugs in through a folder contract
(Table~\ref{tab:iteration_folder}). A trainer reads the masks of
\pth{iteration_N/masks/} and writes checkpoints to
\texttt{models/} and per-pair prediction PNGs to
\texttt{predictions/}, so anything that honours this contract
closes the loop, whatever the framework or the architecture.

\begin{table}[!h]
\centering
\small
\caption{Contents of a single \texttt{iteration\_N/} folder. Each
subfolder has a single producer and a single consumer, and together
they close the annotate/train/predict/review loop.}
\label{tab:iteration_folder}
\begin{tabular}{@{}lll@{}}
\toprule
Subfolder            & Produced by                        & Consumed by \\
\midrule
\texttt{annotations/} & user clicks during round $N$      & training script at end of round $N$ \\
\texttt{models/}      & training script                   & prediction script \\
\texttt{predictions/} & prediction script                 & overlay shown in round $N{+}1$ \\
\texttt{masks/}       & \pth{tools/rasterize.py}          & training script \\
\bottomrule
\end{tabular}
\end{table}

What the trainer needs from the clicks is a per-pixel target, and
one helper produces it. \pth{tools/rasterize.py} reads the pair
files of a round and writes one mask per pair into
\pth{iteration_N/masks/}, giving each clicked pixel its class index
and every other pixel the \pth{ignore_index} declared in
\pth{dataset_metadata.json}. A loss that honours that value scores
only the pixels a human actually looked at, which is what makes
the supervision sparse rather than wrong.

The reference protocol is inherited from iSAGE~\cite{isage}. The
two images of the pair are stacked as input channels and the masks
are the sparse targets. The model is
trained with an error-weighted loss that amplifies the gradient at
each labeled pixel, and nothing is inserted between the clicks and
the loss: no pseudo-labels, no conditional random fields, no
foundation-model prompts. What iSAGE-CD adds is the representation
of the pair, not the training procedure.

\subsection{Iteration workflow}
\label{sec:iteration}

Each round of activity is stored in a numbered
\texttt{iteration\_N/} subfolder
(Table~\ref{tab:iteration_folder}), and while annotating round $N$
the user sees the model of round $N-1$.
The overlay for the pair on screen comes from
\pth{iteration_{N-1}/predictions/<scene>/<before>_<after>.png},
so the surface under review is always the previous round's
predictions for that exact pair. Iteration 0 has no overlay.
Prediction PNGs carry class indices matching
\pth{dataset_metadata.json}, so points and predictions share
one palette. The overlay opacity is adjustable and the \texttt{P}
key shows it while held.

Closing a round is the trainer's job
(Section~\ref{sec:training}): it writes \texttt{models/} and
\texttt{predictions/} of round $N$, creates
\pth{iteration_{N+1}/annotations/}, and increments
\pth{current_iteration}. The next session opens on the new
round with the fresh predictions as the overlay.

Because the annotation tree is the dataset, sharing a round between
annotators is sharing the annotation subtree of one iteration.
\texttt{anotar.py -{}-exportar} zips the JSONs of the current
round, and \texttt{-{}-importar} merges a received zip into the
local session, adding pairs that were absent and overwriting pairs
that exist, the simplest merge rule. In a typical two-person
workflow one annotator exports the round, a reviewer imports it,
revises the points, and exports back or triggers training.
